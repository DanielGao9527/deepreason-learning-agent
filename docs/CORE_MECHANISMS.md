## 1. 它到底是什么

DeepReason 是面向研究、审查和决策任务的本地 Agent 框架模板，知识库是其中一个模块。它尝试把“该走哪条任务路线、需要什么证据、是否允许继续、什么信息值得保留”统一管理。

必须分清两条入口：

- `MultiAgentOrchestrator.run()`：原 CLI 的主要入口，串联路由协调、路由复核、状态图工作流、最终回答和记忆读写。用户关心的大部分机制在这条链上。
- `AgentRuntime.run()`：相对独立的工具循环。我们先前只抽出了它及依赖，做了千问薄适配；这不等于已抽取整个多角色系统。

后续主要沿第一条链学习和改动，已有小型工具循环作为辅助材料保留。2026-09-25 规模核对后建议完整保留上游，不预设必须裁剪；早期范围与评审候选已归档到 `lessons/SCOPE_AND_JURY_PROPOSAL.md`。API 接入由助手处理，不再占用主教学节奏，也不作为读懂框架的先决条件。

## 2. 一次原项目任务怎样经过各部分

用“比较两个技术方案，给出选择依据”作为统一案例，以下描述控制流程，具体路由由模型与规则共同决定，并非已经运行的实验结果。

1. 编排器根据 thread ID 取得近期对话，加载长期记忆。
2. Coordinator 模型返回结构化路由：任务难度、风险、证据是否必需、证据严格度、来源类型和检索查询。
3. Reviewer 模型看到原任务、Coordinator 的路由和记忆，复核是否低估了风险或证据要求。
4. 程序合并路由，然后建立 `AgentState`。工作流节点依次读取、更新同一个状态对象，根据条件选择下一条边；有限重试由代码控制。
5. 检索节点取得资料，证据账本记录来源、位置和内容哈希；审计与门禁决定证据是否满足当前策略。
6. Worker 模型收到任务、状态摘要、门禁结果、证据与记忆，生成最终自然语言回答。
7. 保存近期对话；符合显式记忆请求时尝试长期写入；符合条件的外部证据可以产生沉淀提案。

入口：[multiagent.py](../references/deepreason-full/src/reasoning_agent_template/multiagent.py)，重点 `run:105`、`_call_coordinator_router:1300`、`_call_reviewer:1351`、`_deepseek_messages:1582`。

## 3. 多 Agent 怎样交流，为什么需要它们

当前主要是单进程串行编排，不是很多独立进程通过消息队列自由聊天。

- 模型角色之间：编排器把前一个角色的结构化输出放进下一个角色的输入。例如 Reviewer 收到 Coordinator 的路由 JSON。
- 工作流节点之间：共享 `AgentState`，包括路由、检索结果、证据、门禁决定、验证备注与阶段轨迹。
- 调试界面的角色/交接标签：说明当前节点职责和数据流，不证明每个标签都有独立 LLM、独立会话或自治执行能力。

模型实际调用点主要是 planner、critic、worker；检索、证据审计、门禁、验证等许多节点是 Python 逻辑。`workflow.py:110` 的 while 循环执行节点，`:210` 选择下一条边。默认上限是 32 个工作流步骤、1 次重试额度，具体配置可改。

学习重点是：结构化交付物该包含什么、谁有修改权、共享状态与局部上下文如何取舍、角色失效怎样降级。并发和独立子会话是另一个设计选择，不靠多起几个角色名称获得。

## 4. 审查到底审什么

当前 Reviewer 的主要职责是**路由复核**：是否需要证据，难度/风险是否过低，工作流是否过松。它并非在最后逐句验证报告。

一个值得直接学习的实现是 `multiagent.py:1904` 的 `_merge_reviewer_route()`：

- Coordinator 认为可以轻量回答，Reviewer 认为必须提供证据时，程序可升级证据要求。
- 风险、难度、严格度按更高要求合并；来源取并集，并重新计算工作流。
- Reviewer 给出更弱要求时保留原路线；不是直接把第二个模型的文字当最终决定。
- Reviewer 返回坏 JSON 时，当前保留 Coordinator 路由并标记审查不可用。这是现有降级选择，不等于审查已经通过。

这可以做有价值的比较：总是审查与按风险触发审查，分别产生多少漏判、过度加严、额外调用和延迟。过度保守也可能降低任务完成率，不能只数“拦住了多少”。

工作流里的 `_verify()` 当前主要记录门禁通过；不能把它当独立事实核验器。自然语言 Worker 收到门禁状态后仍主要依赖提示约束，因此“流程门禁通过”和“最终报告全部正确”必须分开。

## 5. 门禁与防泄露是不同职责

`GatePolicy.evaluate()` 当前核对：目标路径是否在工作区、风险对应的证据数量、指定动作是否带审批标识，返回 allow / interrupt / deny。

工作流还会按来源类型和检索分数筛选合格证据，区分软证据策略（不足时有限回答）与严格策略（不足时打回），并对部分保护性动作直接拒绝。见 `workflow.py:517`、`:575`、`:607`。

这提供了可复用的动作判断机制，但不能宣称“已防止数据泄露”。审批字符串不是经过认证的用户身份；来源条数不证明独立性和内容真实；路径限制也不会自动过滤即将发给模型的个人数据。

防泄露要落在数据流上研究：工具与资料访问范围、用户/项目作用域、给模型前的字段选择、不同角色可见的上下文、日志记录内容和执行授权。不能先把不该看的资料交给模型，再指望输出时遮盖就完成隔离。

## 6. 短期记忆、长期记忆、用户画像

短期记忆：`memory.py:33` 保留最近若干问答轮，默认 8 轮，超过后直接截断；编排器默认向提示提供最近 6 轮。`multiagent.py:1688` 能从 SessionStore 恢复近期对话。因此**原编排器已有会话上下文恢复**，而我们抽出的工具 Runtime 仍没有中断步骤续跑，两者不可混说。

长期记忆：`memory.py:71` 按 semantic / episodic / procedural / project / user 保存 JSONL；写入附来源证据、时间与审批标记，经过门禁。同 key 的 `read()` 返回最后记录，但编排器 `multiagent.py:1733` 的实际注入是按分区收集记录后取尾部若干项，没有按当前问题做相关性排序，也不等于自动去重后的最新事实集。

显式写入：`explicit_memory_candidate()` 用“请记住”等触发词提取候选；部分“我的…是…”句式变成字段名。编排器把用户明确请求作为来源证据和审批依据。公共资料与记忆的分流主要靠关键词规则，属于起点，不能当完整语义边界系统。

用户画像值得学。当前 user 分区仅是基础存储，不具备完整的画像抽取、冲突消解、置信度校准或多用户隔离。一个具体候选结构是：

```text
subject_id、scope、field、value、source_event_id、observed_at、
valid_from、valid_until、status、supersedes、explicit_or_inferred
```

这些是拟议设计，不是已实现字段。例如“我平常希望报告简短”可以是长期偏好；“这一次请写详细些”是任务级覆盖，不能直接抹掉长期偏好；用户纠正事实时应保留新旧关联；模型推测不能自动变成用户确认事实。用冲突、撤回、临时覆盖及不同用户案例检验，比多建几个记忆文件更有技术内容。

## 7. 热、温、冷怎样理解

可以作为访问与加载方式的标签：本轮已经在上下文中的信息是热的，按需取回的历史/事实偏温，归档资料偏冷。但这与“短期、长期、知识库”不是严格一一对应。

长期用户偏好加载进当前提示后也处在热上下文里；知识库的热门块也可以缓存。因此先定义存什么、谁能读写、什么时候加载、何时失效，再决定热温冷策略。

核对到的 Hermes 官方实现包括 MEMORY.md、USER.md、会话开始时注入的快照和按需历史检索。本文不把“四层热温冷”说成它唯一的官方架构定义。[Hermes 记忆文档](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory/)

## 8. RAG 实际怎么切、怎么搜

`knowledge.py:374` 按行累积字符，默认目标 1400 字符；超过目标或达到半目标后遇空行就切，保留源文件、行号和内容哈希。没有滑窗重叠；特别长的单行也不会被这个方法内部拆开，所以目标长度不是绝对硬上限。

检索在同一批块上计算多种分数，然后加权合并、按内容去重并取 Top K：

- BM25 风格评分：当前词项使用 set，词频信息被简化，不应直接宣称是完整标准实现。
- semantic：词表/同义词扩展、字符片段特征与余弦相似度，不是调用学习型 embedding 模型。
- graph：词项关联扩展，不是已实现实体关系多跳推理。
- 结果带来源、行号与证据 ID，供审计和后续回答使用。

它值得用来学习检索如何进入证据工作流。检索算法的大规模增强仍优先放在 Fitness；本项目重点是“检索到了内容以后，何时算足够支持当前任务”。

## 9. 自进化不能把几件事混在一起

1. `SelfEvolutionEngine.propose_skill_update()`：接收调用方提供的理由、建议和证据，写出 proposed JSON。不自动分析所有失败，也不直接修改 Skill。
2. `workflow.py:633` 已接通外部证据沉淀提案：门禁允许、来源合格、置信度达到阈值时，调用 EvidenceConsolidationEngine 写出提案；不会因此直接改知识库或长期记忆。
3. 配置编辑器也有草稿/提案/批准应用机制；这是配置变更管理，不能直接等同于从失败经验学习。本文没有把编辑器整条路径运行验收。

读取的默认 run 路径中，没有发现自动调用 SelfEvolutionEngine 形成“失败 → 新技能 → 实际加载 → 新任务验证”的完整链。`skills.py` 主要扫描 SKILL.md 元数据；“发现技能文件”和“实际按需使用技能”也要区分。

我们可以复用提案结构补一个窄闭环：一次具体失败 → 关联原轨迹 → 候选流程与适用条件 → 在正常和反例任务上重新执行 → 决定保留/撤回。这是待做设计，不以更新模型权重为目标。

## 10. 接下来直接学习的顺序

先沿一个任务讲清 **Coordinator → Reviewer → 路由合并 → AgentState → 检索/证据 → 门禁 → Worker**。完整保留固定上游，按实际问题局部重构，不预先剥离外围或把整个编排文件视为展示代码。

**短长期记忆与画像的读写规则**、**有证据的经验提案和验证**仍是核心学习内容。首轮先深入一个机制，最终产物评审是最新候选、尚未实现；按剩余时间安排关联扩展。
