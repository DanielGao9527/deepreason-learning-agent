## 用户提出的评审团：一个可深入的候选

候选位置：multiagent.py 的 Worker 草稿生成之后（当前约 196 行）、对外交付与结果持久化之前（当前约 205 行起）。原 Reviewer 复核路由与策略，新评审机制检查最终产物。前置门禁继续有效。

建议流程：路由协调 → 路由复核 → 检索/证据/门禁 → 草稿 → 独立检查 → 裁决 → 发布、修订或弃权。

| 检查职责 | 必须给出的依据 |
| --- | --- |
| 事实与引用 | 结论对应哪条资料，引用存在且支持结论吗 |
| 矛盾与遗漏 | 是否有反证，是否遗漏用户要求的比较维度 |
| 条件与范围 | 版本、日期、适用条件是否一致，是否过度泛化 |

第一轮各评审读取相同草稿和固定证据，不读取其他评审意见。返回结构化问题，例如 claim_id、issue_type、evidence_id、证据摘录、建议动作。程序可核对资料 ID 和摘录是否存在，但这仍不能完全证明语义蕴含。

裁决器整合证据并输出 publish / revise / abstain，不充当第四张赞成票。一条核实的关键矛盾不能被多数“没问题”抵消；不得覆盖 Gate 或引入未读取的资料。同模型换角色可扩大检查覆盖面，但不能声称各票统计独立。

防止空转的候选规则：最多一次定向修订、一次复核，并设置总调用预算和阶段超时；关键问题仍未解决则保留结论或弃权。评审超时/坏 JSON 记录为缺失，按任务策略有限重试或弃权，不能默认赞成。未通过的草稿可以存为执行历史，不能写成已确认的长期事实。

## 动态权重怎样有依据

不根据模型自报置信度、多数意见或法官自身选择更新权重。先以核实过的案例，分错误类型统计各评审的检出和误报；有样本后再研究带平滑的可靠性估计、最小样本量、上下限与版本回退。

冷启动先使用固定检查职责。更适合首轮探索的动态策略是：根据任务类型与历史表现，分配下一步复核的优先级和预算；权重不直接放行证据不足的答案。参数只在开发集调整，留出集用于最终核验。此处都是候选设计，尚未实现或证明优于基线。

## 最小有效实验

围绕固定资料的软件方案比较，准备包含充分证据、缺资料、版本冲突、错误引用、条件遗漏的案例，预先人工标注可支持的结论与应保留的问题。开发案例和留出案例分开。

对比上游、单次产物审查、评审团加裁决；条件允许再加入等调用/token 预算的多次独立生成或简单汇总，避免把增加调用带来的收益归因于复杂编排。报告正确完成数、错误发布数、弃权数及调用、token、延迟；同时报告覆盖率，保留退步案例。小样本使用分子/分母，不预写提升百分比或显著性结论。

三天内若选择此候选，核心交付可以是结构化评审协议、有界裁决流程、异常处理、固定案例对照。记忆/画像和经验提案仍属于学习全貌；可将核实过的评审失败关联到经验候选，后续验证，不同时承诺所有高级机制落地。

相关研究提供实验动机而非效果保证：[Debate or Vote](https://arxiv.org/abs/2508.17536) 在其七项基准实验中发现简单投票解释了不少辩论收益；[Judging LLM-as-a-Judge](https://arxiv.org/abs/2306.05685) 讨论了位置、冗长和自我偏好等评判偏差。不能据此假定我们的任务必然同样，更不能把法官输出当外部真值。
