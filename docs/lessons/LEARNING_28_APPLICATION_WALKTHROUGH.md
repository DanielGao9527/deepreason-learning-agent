## 1. 先自己跑一遍

在仓库根目录的 PowerShell 运行：

```powershell
.\.venv\Scripts\python.exe scripts\learning_mvp_demo.py
```

不用 API Key，不调用真实千问。终端会直接显示六个问题及回答，然后给出本次结果目录。每次创建独立的 `artifacts/demos/learning-时间-随机号/`，保留真实会话文件、Evidence Ledger、笔记与 Skill 数据库；不重置你原来的学习记录。需要机器摘要时加 `--json`。

本次目录里只要先看两份文件：

- `README.md`：六题预期、实际回答和来源，以及逐步执行过的笔记/Skill 命令、退出码与回执。
- `report.json`：问题的完整运行 payload、节点交付、事件、阶段耗时、实际会话恢复输入与 Skill 提示是否加载。文件路径都属于此次演示目录，不再指向已经删除的临时文件。

模型的路由、生成和复核都是明确的脚本样例；检索、节点流转、发布检查、文件与 SQLite 操作调用真实应用代码。脚本先阻断真实模型工厂，在子进程里也阻断，避免演示误扣额度。**这验收工程接线和状态保护，不是千问效果或教学准确率测试。** guided/deep 的预期是固定脚本路线，不代表任意问法的真实分类结果。

## 3. 会话和笔记：不同状态不能混用

演示先在同一 thread 完成两轮，再启动新的 Python 进程提第三问。检查的不只是文件存在，而是第三轮 Coordinator **实际收到前两轮问题**，最终快照有三轮。这个第三问是固定概念题；没有验证模型能正确理解指代词或依据历史推断新意图。会话保护、进程退出和写失败的深入反例仍见第二十五课。

笔记用真实 `run_learning.py` CLI，每一步都启动新进程：

1. 查看空笔记，version=0。
2. 用 `note-1` 和 expected_version=0 提交，得到 created、version=1。
3. 相同操作 ID/正文重复提交，得到 replayed、同一 note_id，笔记仍一条。
4. 再启动进程核对回执；同 ID 改正文、新 ID 配旧 thread 版本都退出 2，不写第二条。
5. 显式保存比较题反馈，才产生第二条笔记。普通提问没有自动写笔记。

这些操作沿用上游 Tool Runtime 的注册、参数和 Gate；持久回执与 thread 版本来自本项目笔记适配器。问答模型没有自主选择或调用笔记工具。按 thread 隔离也不等于有登录用户认证。

## 4. Skill：检查是否生效，更要检查旧审批

从第二条明确反馈提出两个相同内容的候选：二者都只是 proposed，生效版本仍是 0。用比较题实际运行 Worker，提示不含教学 Skill。错哈希批准退出 2；显式正确批准第一个候选后为 version=1，同题新会话的 Worker 提示出现规则。第二个旧候选因基础状态已变被拒绝。回退 version=0 后提示不再含规则。

这次串联还复现并修复一个真实缺陷：

```text
旧实现：基线 A → 批准 B → 回退 A → 旧候选的 base_hash 又匹配 → 意外批准
新实现：基线 revision=0 → 批准 revision=1 → 回退 revision=2
        旧候选仍绑定 revision=0，内容虽相同也拒绝
```

回退恢复的是内容版本，审批状态修订号不能倒退。这常称为 ABA 问题：只看“现在又是 A”会漏掉中间已经发生过的状态变更。

本项目在 SQLite 的同一 `BEGIN IMMEDIATE` 事务内检查并更新修订号；提出候选保存 `base_revision`，批准要求当前基础哈希与修订号同时匹配。提出候选时也检查读取期间是否发生过批准/回退。同内容重发为新版本仍会使旧候选失效。新提出的候选经重新审核可以正常批准，不永久封禁这条规则。

旧数据库自动保留活动版本与历史；**没有基础修订号的旧待批候选必须重新提出**，返回 `candidate_requires_reproposal`，不猜测其审批上下文。四项新增回归分别覆盖回退后的旧候选、相同内容的新版本、旧数据库迁移、提出候选期间的交错变更。

这只是本机合作入口的候选审批绑定，没有防止用户直接编辑数据库。回退命令仍核对当前内容哈希，没有新增通用审批票据/身份认证。Skill 固定模板和三例触发检查均沿用原实现；本轮只证明提示加载和状态边界，**没有证明答案变好**。
