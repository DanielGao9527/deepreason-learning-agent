# 第十八课：只在 Top-K 截断时补查一次

这是开发路径 B 的第二小步。比较题原本分别检索两个主体；若某侧的前四个候选都未包含该主体，即使相关片段排在第五或第六，也会止答。本课让 Retriever 在**有截断迹象**时扩大一次候选范围，同时维持证据门槛和中断边界。

## 原问题与判定

学习场景默认 `top_k=4`、`min_score=0.08`。在固定的离线夹具中，五份写着“满 二叉树”的干扰片段排名靠前，却没有完整词组“满二叉树”；真正定义片段排在其后。原三任务计划的 `lookup_left` 因前四条都不含主体而失败，`join_evidence` 阻断，Worker 不运行。这是**候选截断**，与完全没有源文件不同。

补救只在 `len(初次候选) == top_k` 且没有字面主体时触发：对同一 query、同一 BM25/词项相似度/共现配置、同一 `min_score` 再读一次，`top_k` 从 4 扩到最多 12。没有改写问题、降低分数阈值、调用外部网页或增加模型路由。每个主体最多两次本地检索；`max_steps=3` 仍指三个计划任务，检索预算由新增的 `max_retrieval_attempts_per_subject` 单独限制。计划进入运行前拒绝越界预算。候选不足四条时再加大 Top-K 没有意义，直接保留止答。

每次检索的候选数、主体命中数和 Top-K 写入任务产物；发生第二次读取时增加 `retrieval_recovery_attempted` 事件。最后仍要经过原有 `retrieve → reason` 交付校验、证据资格、Gate 和发布策略。字面主体命中不证明结论正确。

## 前提变化与超时

比较计划启动时对本地 `.md/.txt/.json` 源文件名和文件字节建立 SHA-256 指纹；每次检索后、Worker 前和最终发布/会话保存前复查。若资料在这些边界发生变化，抛出 `LearningCorpusChangedError`，失败文件标为 `precondition_changed`，不发布旧答案、不保存该轮会话。检索抛超时则标为 `retrieval_unavailable`，不再重试或调用 Worker。这个保护只覆盖当前双主体比较计划；它不是跨进程事务锁，不能回滚检索阶段已写入的 Evidence Ledger，也不能证明其他时刻或普通题没有竞态。

## 同初态开关对照

`scripts/eval_bounded_recovery.py` 对每个场景复制相同语料、创建全新会话与脚本模型，唯一改变的是每主体允许 1 次还是 2 次读取；两侧语料指纹必须一致。六次离线运行均没有真实千问请求。

| 场景 | 预算 1 的结果 → 预算 2 的结果 | 本地检索调用 | 脚本模型调用 |
| --- | --- | --- | --- |
| 两侧定义本就在前四条 | answered → answered | 2 → 2 | 3 → 3 |
| 定义被 Top-K 干扰片段挤出 | abstained_incomplete_evidence → answered | 2 → 3 | 2 → 3 |
| 语料确实缺左侧定义 | abstained_incomplete_evidence → abstained_incomplete_evidence | 2 → 3 | 2 → 2 |

这个结果只证明小夹具里的**条件性可达性**：多一次本地检索恢复一个被截断的定义，同时真正缺资料仍止答。它不证明答案语义正确率、全局召回率或延迟提升。实际语料中的“满二叉树／完全二叉树”仍缺完整的一侧定义，即使扩到 12 也会止答。`scripts/verify_learning_paths.py` 加入第八个恢复验收案例；八个案例观察到的完整节点序列依然只有一种，恢复发生在 `retrieve` 节点内部，并没有新增可达工作流边。

测试还注入了检索期间新增文件、检索后 Worker 前修改文件、Worker 生成文字期间修改文件，以及补查超时：相应轮次无会话快照；迟到的 Worker 文字不进入发布。测试位置：`workbench/deepreason/tests/test_learning_mvp.py`。代码位置：`learning_plan.py` 的预算校验、`learning.py` 的补查与源版本检查、`multiagent.py` 的发布前钩子。上游复用检索器、Ledger、Gate、编排与会话模块；上述有限补查、版本边界和对照脚本由本项目与 AI 协作新增。

下一阶段 C 不应直接宣称“可靠工具执行”：上游 Runtime 只有内存去重；要先为一个明确的学习记录写动作做参数/权限、持久幂等、超时后的结果核对与重启实验。
