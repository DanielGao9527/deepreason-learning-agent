# 第十二课：多角色链路为什么慢，怎样看真实耗时

更新：2026-09-25。依据用户在 PowerShell 实测的两题，以及 `learning_mvp/sessions/default/snapshot.json` 中最后一题的事件。没有为这次分析再调用千问；用户手测后本机累计为 12/100。会话快照只保留最近一轮事件，较早的“二叉树是什么”已没有完整逐节点耗时，因此不推测它的精确秒数。

## 这算不算 Multi-Agent

这是**按职责分工的串行多角色 Agent 编排**。同一千问模型分别以 Coordinator、Reviewer、Worker（严格题另有 Output Reviewer）的不同输入契约参与决策；检索、Gate、状态机和发布保护是确定性代码。不是多个异构模型并行协作，也没有多个自治进程相互通信。源码主链在 `workbench/deepreason/src/reasoning_agent_template/multiagent.py:107`；学习场景的覆盖在 `learning.py:133`。

屏幕上的 `intake -> plan -> retrieve...` 是**状态节点顺序**，不能直接当耗时图，也不能认为每个节点都调用模型。实际耗时在顶层 `events` 的 `duration_ms`。根目录 `run_learning.py` 从这次起会在每轮回答下打印可测的路由、复核、检索、回答生成及严格题答案复核耗时，并保留总耗时。严格题的最后一次 Reviewer 计时是本轮新补的事件，之前的会话没有这一字段。

## 最后一轮“什么是哈希冲突”的实测拆分

| 步骤 | 事件 | 实测 |
| --- | --- | ---: |
| Coordinator 路由模型 | `llm_routing` | 8.107 秒 |
| Reviewer 路线复核模型 | `route_review` | 19.441 秒 |
| 本地检索 | `stage_completed: retrieve` | 0.033 秒 |
| Worker 生成模型 | `llm_completed` | 14.316 秒 |

这四项合计约 41.90 秒，三次串行模型请求贡献几乎全部可见耗时。其他节点的轻量处理和输入输出不在这个合计内，因此不能把 41.90 秒精确称为端到端总时间。终端新增的“总计”来自同一轮 `payload.duration_ms`，今后能直接看到端到端数值。严格题通常还会多一次最终评审模型请求，因此可能更慢；仍需逐题计时，不预设加速幅度。

## 为什么“二叉树是什么”止答

本地无模型检索实验显示，提问“二叉树是什么”时 `02_search_tree.md` 命中：综合分 0.644、BM25 子分 1.0、语义子分 0.087885。`workflow.py:_has_strong_local_rag` 要求综合分至少 0.45 **且**语义子分至少 0.10；该问题在第二个条件失败。软证据 Gate 仍可 `allow`，但 `LearningOrchestrator._call_deepseek` 发现合格证据为空，跳过 Worker，所以本轮只发了路由和 Reviewer 两次千问请求。用户看到的 `allow` 与 `abstained_no_evidence` 并不矛盾：前者是软门禁允许受限交付，后者是学习助手不允许无依据的确定性回答。

此外，现有六份资料主要讲二叉**搜索**树，缺“二叉树”的独立定义。直接把语义阈值调低并不一定是正确修复，可能放进不相关材料。下一步应先补有出处的二叉树入门资料，建立“二叉树/二叉搜索树/无关题”三类人工标签，再比较现阈值、查询改写或其他召回方案的正确止答与误命中。当前不能写“检索准确率提升”或“已优化延迟”。

## 有根据的提速路线

1. **先量化**：按题记录端到端耗时、各模型耗时、请求数、回答/止答结果和来源相关性；区分 guided 与 deep。
2. **做对照**：对简单题试“不发路线 Reviewer”或使用更快的路由模型，与现方案在同一批问题上比较错误路线、资料外误答、耗时与成本。若复核能拦住真实错误，不能只为省一次调用就删除。
3. **避免错误优化方向**：当前检索仅约 33 毫秒。更换向量库或重写 BM25 不太可能解决本轮 40 多秒的等待。

这一课属于诊断和观测，尚未实施路由模型替换或跳过 Reviewer 的策略。
